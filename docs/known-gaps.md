# Sampolio — Known Gaps & Defects

Factual defects, dead code, stale comments, and missing pieces **as of the current
codebase**. Everything here is verified against the code (file + line/symbol given)
or observed in the running app. Design-level limitations (no file locking, no
cross-currency conversion, single-node assumptions, the cookie-presence rate-limiter
tradeoff) live in `AGENTS.md` §Safety, testing, and operations; forward-looking ideas live in
[`improvements.md`](improvements.md).

## Open gaps

| # | What | Notes |
|---|---|---|
| 1 | **Backup automation lives outside the repo.** The daily backup (a launchd agent plus a backup script kept outside the repo) is not version-controlled with the app. Accepted for now — see [`operations.md`](operations.md) §6. | External to repo |
| 2 | **No end-to-end tests; component coverage is partial.** Pure engines, schemas, the db layer, a representative action-layer slice, the shared UI primitives, and the three highest-state components (cashflow item modal, split editor, reconcile wizard) are covered (~100 vitest files); most pages and server actions still have no automated coverage. The passkey flow (sign-up → password sign-in → add passkey → passkey/conditional-UI sign-in → rename/delete) was smoke-tested once with Playwright + a CDP virtual authenticator, but no browser suite is committed. Tracked as [`improvements.md`](improvements.md) §13.1. | `src/**/*.test.{ts,tsx}` |
| 3 | **Demo-mode masking depends on components re-rendering.** `formatCurrency` reads a process-wide flag, so any new memoized surface can cache unmasked text: ECharts `option` `useMemo`s must list `demoMasked` in their deps, any other `useMemo`'d money string must either list it or format at render time, and long-lived PrimeReact `DataTable`s need a `key={demoMasked ? 'masked' : 'plain'}` remount. Not a bug in current code (all call sites comply) — a **convention future code must follow**; see [`docs/features.md`](features.md) §10 and [`src/components/AGENTS.md`](../src/components/AGENTS.md). | `src/lib/demo-mode.ts`, chart/table call sites |
| 4 | **Jiggle reorder has no vertical edge auto-scroll (v1).** Dragging an item near a viewport edge does not auto-scroll the page, so reordering a long list relies on ordinary page scroll (or the sr-only arrow-key entry buttons). Acceptable for the short group/bank-account lists it drives today. | `src/components/ui/jiggle-reorder.tsx` |
| 5 | **Indistinguishable bank rows lack individual identity.** The merge preserves the number of identical rows returned in a complete fetch, but cannot distinguish legitimate identical purchases from bank-side duplicate delivery or identify which identical occurrence disappeared. Booked history is retained, except a stored extra occurrence slot (`#occN`) that a fetch reporting fewer identical copies disproves. Reference-less synthetic keys retain their established content-based semantics. Repeated deliveries are collapsed to the maximum count within one page or request (`collapseRepeatedDeliveries`), so genuine identical purchases delivered on different pages of one response collapse to one row, and the merge then also drops a previously stored extra slot for them. | `src/lib/bank/dedup.ts`, `mergeTransactions`, `collapseRepeatedDeliveries` |
| 6 | **Split storage: auth in SQLCipher, everything else in `.enc` files.** Users/sessions/accounts/passkeys live in `sampolio.db`; all financial data (and `app-settings.enc`, `preferences.enc`) is still file-based. The full-data migration follows the per-module pattern in [`src/lib/db/AGENTS.md`](../src/lib/db/AGENTS.md). | `src/lib/db/sqlite/`, `src/lib/db/users.ts` |
| 7 | **Brute-force lockout is in-memory and per process.** `isAccountLocked` / `recordFailedLogin` (`src/lib/db/users.ts`, also keyed `pw:<userId>` for `changeMyPassword`) and the sign-up action limits (`src/lib/rate-limit.ts`) reset on restart; Better Auth's own HTTP rate limits are DB-backed (`rateLimit` table). The `/passkey/*` routes are covered only by the rate limits, not the per-email lockout (they carry no email). | `src/lib/db/users.ts`, `src/lib/auth/server.ts` |
| 8 | **No passkey attestation.** Registration uses `attestation: "none"` (plugin default), so AAGUIDs are often all-zero (Apple); the default name then falls back to the registering browser ("Safari on iPhone"), which says where the passkey was created, not which password manager holds it; users can rename. Authenticator model is not verified. | `@better-auth/passkey`, `src/lib/passkey-name.ts` |
| 9 | **No invite/consent step for shared entities.** An owner adds a member to a split group or shared mortgage directly by account email; the added user never accepts. Split lookups return the generic `MEMBER_LOOKUP_ERROR`, but `addMortgageMemberByEmail` still distinguishes "No active Sampolio account uses that email yet" from "already a member". | `src/lib/actions/split-groups.ts` (`createSplitGroup`, `addSplitGroupMember`), `src/lib/actions/shared-mortgages.ts` (`addMortgageMemberByEmail`) |
| 10 | **Split member emails are visible to every member.** `getSplitGroupView` returns the full `group` (each `SplitGroupMember.email`) to any member, not only owners. | `src/lib/actions/split-groups.ts` `getSplitGroupView`, `SplitGroupMember` in `src/types/index.ts` |
| 11 | **Bank-anchor limits.** An available/expected balance can include an overdraft or credit facility the ledger cannot show, so it stays inside the anchor's month-start balance. A bank that only serves a **historical** available balance (as of an earlier day than the sync) never re-anchors the account: that estimate is not stored and the previous anchor stays. Two non-excluded cash/savings links anchoring the same `FinancialAccount` each write the one current-month snapshot with their own balance (last sync wins) while their ledgers are merged. | `src/lib/live-anchor.ts` (`bankSnapshotProvenance`), `src/lib/bank/sync.ts` (`autoAnchorAccount`, `getLinkedCashLedger`) |
| 12 | **A manual current-month check-in on a bank-linked account must be a start-of-month balance.** A manual snapshot is the month's opening by definition, and the current anchor month then starts at that balance plus every booked row of the month; typing today's live bank balance instead counts those rows twice until the next sync overwrites the snapshot (last write wins). Nothing in the wizard distinguishes the two. | `src/lib/live-anchor.ts` (`anchorMonthOpeningBalance`, `anchorMonthActuals`), `src/components/reconcile/reconcile-wizard.tsx` |
| 13 | **Sidebar collapse animates layout properties.** The desktop sidebar transitions `width` and the content column `margin-left` (both `--motion-slow`, off under reduced motion) rather than a transform, short of the opacity/transform-only motion rule in [`architecture.md`](architecture.md) §17. | `src/components/layout/sidebar-nav.tsx`, `src/components/layout/app-layout.tsx` |
| 14 | **Month-start balance is frozen at sync time.** `monthStartBalance` is computed once from that sync's ledger. When the balance predates the month (`balanceAsOf` before the 1st, e.g. last month's `CLBD`), rows the bank posts later but dates between `balanceAsOf` and the month start never update it, so the forecast's opening and the retrospective seed miss them until the next sync writes a new snapshot. | `src/lib/live-anchor.ts` (`bankSnapshotProvenance`, `startOfMonthFromLive`) |
| 15 | **A stale bank-sync anchor only actualizes its own month.** When syncing stops, the last bank-sync snapshot stays the anchor: its month is actualized, but every later month up to today is forecast in full, ignoring booked rows the ledger may still hold for them. | `src/lib/live-anchor.ts` `shouldActualizeAnchorMonth` |
| 16 | **Sync fetch windows use the UTC date.** `todayYmd` in the sync engine takes the UTC calendar date for `date_from`, the pending-reconcile and card-refresh floors, and the once-a-day refresh check, while booking-date fallbacks, snapshot months and as-of dates are server-local; right after local midnight the two differ by a day. | `src/lib/bank/sync.ts` `todayYmd`, `subDaysYmd` |
| 17 | **Account deletion is not transactional.** `deleteMyAccount` leaves or deletes split groups (each re-checked under its group lock) and then mortgages one at a time; a later refusal or failure leaves the earlier groups already left, and the mortgage steps take no lock. | `src/lib/actions/account.ts` `deleteMyAccount` |
| 18 | **Pruned occurrence overrides do not come back.** Compaction and `cleanupExpiredOverrides` delete overrides before the anchor-based cutoff; if a later snapshot deletion moves the anchor earlier, the months they covered are forecast again from the plain recurring item. | `src/lib/maintenance-utils.ts` `expiredOverrideCutoff`, `src/lib/actions/maintenance.ts`, `src/lib/actions/planned.ts` |
| 19 | **Injected budget/goal expenses are not matched to their bookings.** In an actualized anchor month, `budget` and `goal` lines use the `'none'` policy and stay at their planned amount, so a budget or goal payment that has already booked is deducted twice (once in the month's booked rows, once as the injected line). | `src/lib/projection.ts` (`calculateProjection` policy assignment), `src/lib/current-month-actuals.ts` |
| 20 | **Partial, split or over-tolerance payments keep the full obligation forecast.** Matching pairs one forecast line with one booked transaction within `max(€1, 5%)`; a bill paid in two parts, or paid at a different amount, leaves the line unmatched (an `'exact-only'` line stays at its full amount; a `'full'` line is only reduced through its category's gap blend). | `src/lib/current-month-actuals.ts` (`ACTUAL_AMOUNT_TOLERANCE_ABS`/`_PCT`) |
| 21 | **A Playground amount change on an already-paid item loses its match.** The modified run re-matches its own lines, so changing a paid item's amount beyond the tolerance turns it unpaid and forecasts it again in the anchor month. | `src/lib/actions/scenario.ts`, `src/lib/current-month-actuals.ts` |
